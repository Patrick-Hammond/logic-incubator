# tilemap

Vendored from [`@pixi/tilemap`](https://github.com/pixijs-userland/tilemap) 3.2.1 (MIT, Ivan Popelyshev - see `LICENSE`), the oldest release under the scoped package name and the last one whose runtime API (`Geometry.addAttribute`, the 3-arg `Buffer` constructor, `ObjectRenderer`/`Resource` shapes) matches pixi.js 5.2.1, the version this project is pinned to.

## Why vendored instead of an npm dependency

This project previously depended on the unscoped `pixi-tilemap@2.0.6` package (abandoned since Oct 2020) and patched three bugs into its compiled `dist` output via `patch-package` (see git history for `patches/pixi-tilemap+2.0.6.patch`). That stopped scaling once shader changes (for tile lighting) were on the table: patching a minified bundle by string-matching compiled ES5 isn't a reasonable way to develop a shader feature, and there is no upstream to stay in sync with either way - `pixi-tilemap` never moved past 2.1.4 (2020), and the actively maintained `@pixi/tilemap` line moved on to target pixi.js v7/v8, which this project isn't on.

## What changed from upstream 3.2.1

- **Import paths** consolidated from the individual `@pixi/core`, `@pixi/display`, `@pixi/math`, `@pixi/constants`, `@pixi/utils` packages to the single `pixi.js` package, matching how the rest of this project imports pixi and avoiding a dependency on `@pixi/*` sub-package versions this project doesn't otherwise pin.
- **Canvas rendering removed** (`CanvasTileRenderer`, and the `renderCanvas`/`renderCanvasCore` methods on `Tilemap`/`CompositeTilemap`). This project only ever uses the WebGL renderer, and `@pixi/canvas-renderer` isn't among the `@pixi/*` versions pinned in the root `package.json` overrides - pulling it in transitively would risk the exact "two engine instances" problem those overrides exist to prevent.
- **Deprecated back-compat aliases removed** (`addFrame`, `addRect`, `setBitmaps`, `texPerChild`, and the old `CompositeRectTileLayer`/`RectTileLayer` class names). Call sites in this codebase (`Player.ts`, `TileMap.ts`) were updated to call `.tile(texture, x, y)` directly instead.
- **Two bugs fixed**, both present in upstream 3.2.1 as shipped (and, for the first one, still present in the pixi.js-v8-targeting `@pixi/tilemap` 5.0.2 as of 2025 - this isn't version-specific, it's a long-standing upstream defect):

  1. **Trimmed/tightly-packed frames sampled past their own edges.** `Tilemap.tile()` defaulted `tileWidth`/`tileHeight` to `texture.orig.width/height` - the sprite's *untrimmed* logical size - instead of `texture.frame.width/height`, the actual packed pixel rectangle. For an untrimmed atlas `orig` and `frame` are the same size, so this was invisible; for a trimmed, tightly-packed atlas (no padding between frames), it sampled a few pixels past the real edge of the frame into whatever was packed next to it, and drew the tile oversized to match. Fixed by defaulting to `texture.frame.width/height`, and offsetting the draw position by `texture.trim.x/y` (0 when untrimmed) so a trimmed frame still lands where a plain `Sprite` would draw it - mirroring the `w1 = trim.x - anchor*orig.width` math `Sprite.calculateVertices` does internally for an anchor of `(0, 0)`, which is what `tile()` always assumes.
  2. **`tileRotate` wrote to the wrong buffer slot.** It computed the target index as `POINT_STRUCT_SIZE - POINT_STRUCT.TEXTURE_INDEX`, i.e. it was self-referencing every other setter's own field except this one - every other tile setter (`tileAnimX/Y`, `tileAnimDivisor`, `tileAlpha`) correctly builds its offset from its *own* enum member. Rotating a tile was corrupting which texture it samples from instead of rotating it. Fixed to reference `POINT_STRUCT.ROTATE`.

- `settings.ts` dropped the `maxTextures`/`boundSize`/`boundCountPerBuffer` backward-compat getters/setters for pre-3.0 property names (themselves inconsistent upstream - `boundSize`'s setter and getter didn't even agree on which property they touched) since nothing in this codebase used the old names.

## Per-tile lighting: `tint` and `flicker`

Added on top of upstream, for the tile-lighting feature: two more `TileOptions` fields, threaded through the same `POINT_STRUCT` / vertex-buffer / shader pipeline as the existing `alpha`.

- **`tint`** - a packed RGB hex colour (e.g. `0xffaa55`), same convention as `DisplayObject.tint` elsewhere in pixi. Decoded to three floats once in `tile()` and uploaded as a new `aTint` vertex attribute; the fragment shader multiplies it into the sampled colour (`gl_FragColor = color * vAlpha * tileAlpha * vec4(vTint * brightness, 1.0)`), so `0xffffff` (the default) is a no-op and darker/coloured values dim or tint the tile - the mechanism for "this tile is lit to this colour/brightness."
- **`flicker`** / **`flickerSeed`** - an intensity (`0` = steady) and a per-tile phase seed, also a per-vertex attribute (`aFlicker`). The animation itself happens entirely in the fragment shader, driven by a single `time` uniform (`performance.now()`, wrapped modulo 10000 to avoid `sin()` precision loss over a long play session) - a stepped, interpolated pseudo-random hash (`tilemap.frag`'s `hash()`) turns `time` and the seed into a brightness multiplier. This was a deliberate choice over animating it from the CPU side: since tiles are cleared and re-added every frame in this codebase's render loop anyway, updating a per-tile flicker value would mean touching the vertex buffer every frame just for the animation - a single scalar uniform upload is effectively free by comparison, and keeps the flicker smooth even at a lower tile-rebuild rate. `flickerSeed` defaults to a hash of the tile's own `(x, y)`, which is only frame-stable if that position is itself frame-stable - see the doc comment on `TileOptions.flickerSeed` for why a screen-space tile (e.g. anything positioned relative to a panning camera) needs an explicit seed derived from a stable coordinate instead.

## Bug found alongside this: container `alpha` never reached the shader

Same root issue as the old `pixi-tilemap` 2.0.6 "Fix 1" (no alpha support), independently present in upstream 3.2.1: `Tilemap`/`CompositeTilemap.render()` never read `this.worldAlpha` into the shader at all. Upstream 3.2.1 does have a *per-tile* `alpha` (the `aAlpha` attribute passed via `TileOptions.alpha`), but this codebase's z-band fade (`TileMap.ts` setting `.alpha` on the containing `Container`) relies on the older, container-level mechanism, which PIXI computes into `this.worldAlpha` automatically but which nothing in `render()` ever consulted - so bands stopped fading out entirely once this library was swapped in. Fixed by adding a `tileAlpha` uniform, set from `this.worldAlpha` in both `Tilemap.render()` and `CompositeTilemap.render()` (mirroring the old library's fix exactly), multiplied into the final colour alongside the per-tile alpha and tint.

## Regenerating from a newer upstream

If a future `@pixi/tilemap` release fixes bugs worth pulling in and still targets pixi.js v5-compatible APIs (unlikely, given the v6/v7/v8 direction upstream has taken - see the pixi.js version research in this project's history), diff its `src/` against this folder rather than replacing wholesale, to keep the import-path and canvas-removal changes above.
